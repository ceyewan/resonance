# Logic 设计

> 本文档描述 Resonance 中 Logic 服务的职责、边界和核心处理路径。阅读完本文后，应该能回答三个问题：为什么所有主事实都必须在 Logic 落地；Outbox 为什么必须属于 Logic；以及当前统一事件入口在 Logic 中已经实现到了什么程度。

---

## 1. Logic 的定位

Logic 是 Resonance 的业务核心层。系统中所有真正会改变主事实的动作，都应该收敛到这里完成。对于 IM 系统来说，所谓主事实包括消息本身、消息序列、会话成员关系、已读位点以及未来的撤回和编辑状态。谁可以发送消息、谁属于某个会话、一个事件应该分配什么 `seq_id`、什么时候算真正成功，这些都不应该由 Gateway 决定，更不应该由 Task 在异步消费时临时判断，而应该在 Logic 中一次性判定清楚。

从整个系统来看，Logic 的作用不是“把请求接过来顺手写库”，而是把业务规则、事务边界和可靠投递绑在一起。只有这样，系统才能在同步 Ack 和异步扩散之间维持清晰语义：发送方拿到 Ack，代表主事实已经成立；后续事件扩散和在线送达则由异步链路继续推进。

---

## 2. 设计目标

Logic 的设计主要服务于三件事。第一件事是收敛业务规则，让“谁能做什么”只有一个权威判断入口。第二件事是收敛主事实写入，让所有会改变系统权威数据的动作都落在统一事务边界里。第三件事是收敛可靠投递，让一条已成立的业务动作一定能进入异步链路，而不是靠调用方自己碰运气补偿。

这三件事共同决定了 Logic 的角色：它不是接入层，也不是异步层，而是系统中“事实如何成立”的唯一中心。只要某个能力会改变主事实，它就应该优先思考自己是否应该进入 Logic，而不是顺手挂在 Gateway 或 Task 上。

---

## 3. 运行时位置

在当前架构中，Logic 位于 Gateway 和 Task 之间。Gateway 把客户端请求转成内部 gRPC 调用交给 Logic，Logic 在这里完成业务校验与事务处理，再通过 Outbox 和 MQ 把事件交给 Task。

### 3.1 架构图

```text
Gateway ── gRPC ──▶ Logic ── PostgreSQL / Redis
                        │
                        └── Outbox + MQ(NATS) ──▶ Task
```

### 3.2 Logic 在主链路中的作用

- 接收 Gateway 转发来的已认证请求
- 完成权限判断与业务规则校验
- 生成事件 ID、序列号和统一事件对象
- 在事务内写入主事实与 Outbox
- 返回同步 Ack
- 异步把事件交给 Task 扩散

从这个位置可以看出，Logic 是同步业务链路的终点，也是异步事件链路的起点。

---

## 4. 职责边界

### 4.1 负责什么

| 职责 | 说明 |
| ---- | ---- |
| 业务规则 | 判断谁能发送、谁能加入会话、谁能操作某条消息 |
| 权限校验 | 根据当前用户与会话状态判断动作是否合法 |
| 主事实写入 | 写消息主表、推进序列、更新会话状态等 |
| 统一事件生成 | 构造 `ChatEvent` 与 `MQEvent` |
| 事务边界 | 把主事实写入与 Outbox 写入放在同一事务中 |
| 可靠投递起点 | 通过 Outbox 与 MQ 把事件交给异步层 |
| 在线状态汇总入口 | 通过 Presence 服务管理系统共享在线状态 |

### 4.2 不负责什么

| 不负责的事情 | 原因 |
| ------------ | ---- |
| 协议适配 | 这是 Gateway 的职责 |
| WebSocket 连接管理 | 这是 Gateway 的职责 |
| 写扩散 | 这是 Task 的职责 |
| 在线推送 | 这是 Task + Gateway 的职责 |

这张表的重点，在于明确 Logic 只做“主事实成立”相关的事情。一旦某个逻辑需要同时考虑连接、推送、消息广播和业务校验，它就应该被拆开，而不是继续堆进 Logic。

---

## 5. 统一事件入口

当前 Logic 中最重要的业务入口，是 `ChatService.SendEvent`。它不是一个单纯的“发送消息接口”，而是统一事件入口的雏形。当前代码路径位于 `logic/service/chat.go`。

### 5.1 当前处理流程

```text
Gateway 调用 SendEvent
  ├── 从 context 中读取已认证 username
  ├── 查询会话成员并校验权限
  ├── 生成 event_id / seq_id
  ├── 构造 ChatEvent
  ├── 构造主事实模型（当前主要是 MessageContent）
  ├── 事务内写主事实 + Outbox
  ├── 异步尝试发布 MQ
  └── 返回 Ack
```

### 5.2 这条路径说明了什么

这条路径说明，Logic 首先解决的是“是否允许”，其次才是“如何落地”。只有用户身份和会话权限都成立，后续的事件生成和事务写入才有意义。同时，这条路径也说明统一事件入口的方向已经非常清楚：客户端上来的业务动作，不再只是“发消息”，而是逐步向“提交一个会话事件”演进。

### 5.3 当前实现状态

这里必须明确说明现状：虽然协议层已经把 `ChatEvent` 设计成统一载体，但当前 `logic/service/chat.go` 里完整打通的主要还是 `message`。对于 `recall`、`edit` 等其他 payload，系统当前更多是协议预留和后续演进方向，而不是已经完全成熟的业务闭环。因此，当前 Logic 已经不是传统意义上的“纯消息服务”，但也还不是一个所有会话事件都已经同等成熟的统一事件服务。

---

## 6. Outbox 与事务一致性

Outbox 是 Logic 设计中最关键的一层保证。它的存在不是为了“多一张表”，而是为了把“业务已经成立”和“事件必须被异步层接住”绑定到同一个事务结果上。对于消息发送来说，如果主事实已经提交但系统忘了投递，接收方就会永远收不到；如果事件已经投出但主事实没有提交，系统又会产生另一种不一致。Outbox 解决的，正是这两种断裂之间的问题。

### 6.1 为什么 Outbox 必须属于 Logic

Gateway 不了解一条业务什么时候算真正成功，它只能看到接入层请求；Task 是在事务已经结束之后才介入的，它只能消费已存在的事件，而无法反过来保障业务主事实与投递记录的一致性。只有 Logic 同时掌握业务规则、数据库事务和即将投递的事件内容，所以只有它适合承担 Outbox 的责任。

### 6.2 一致性链路图

```text
业务请求
  └── Logic
      ├── 事务内：写主事实
      ├── 事务内：写 Outbox
      ├── 事务提交成功
      └── 事务外：异步投递 MQ
              └── 失败时由 Outbox 补偿任务兜底
```

### 6.3 当前实现落点

- `logic/service/chat.go`：构造事件并发起主链路处理
- `repo/message.go`：事务内写消息主事实与 Outbox
- `logic/job/outbox.go`：定时补偿与重投

这三部分共同组成了 Logic 对“主事实成立之后，事件必须最终进入异步链路”的保证。

---

## 7. 其他业务职责

虽然 `ChatService.SendEvent` 是最典型的统一事件入口，但 Logic 的职责并不只限于发消息。会话列表、历史拉取、联系人搜索、创建会话、更新已读位点、在线状态同步，这些能力同样说明了 Logic 的定位：要么读取主事实，要么推进主事实变化。

例如更新已读位点的核心，不是“立即通知别人我已读了”，而是先把当前用户在某个会话中的已读位置作为权威状态更新下来。类似地，在线状态同步也不是单纯的连接层行为，而是系统共享状态的一部分，所以 Gateway 感知到连接变化之后，仍然通过 Presence 服务把这部分状态汇总到 Logic。

---

## 8. 当前实现结构

当前 Logic 的主要实现落点包括：

- `logic/logic.go`：服务装配与生命周期管理
- `logic/server/grpc.go`：gRPC server 注册
- `logic/server/interceptor_auth.go`：从 `x-username` metadata 恢复身份并写入 context
- `logic/service/auth.go`：登录、注册与 JWT 签发
- `logic/service/chat.go`：统一事件入口（`SendEvent`），当前完整打通 `message` payload
- `logic/service/session.go`：会话创建与成员管理
- `logic/service/history.go`：历史消息拉取
- `logic/service/inbox.go`：Inbox 增量拉取（`PullInboxDelta`）与未读数统计
- `logic/service/contact.go`：联系人搜索
- `logic/service/presence.go`：在线状态同步
- `logic/internal/mqpublish/publish.go`：Outbox 异步发布 MQ 的内部封装（供 chat.go 和补偿任务复用）
- `logic/job/outbox.go`：Outbox 定时补偿任务
- `logic/event/`：Phase 5 预留，统一事件处理骨架（当前为空占位包）

这些文件共同体现了一件事：Logic 当前实现已经明确围绕业务与事务组织起来，而不是围绕协议入口或底层连接器零散拼接。

## 10. 小结

如果用一句话概括 Logic，那么它是 Resonance 的事实判定与事实生产中心。它不负责连接，也不负责推送，但它负责决定事实是否成立、事实如何编号、事实如何持久化，以及事实如何进入可靠的异步链路。只要这个边界持续成立，后续新增事件类型时，系统就只需要在同一套骨架上补齐新的业务处理逻辑，而不需要再创造一层新的核心服务。
