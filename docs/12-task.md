# Task 设计

> 本文档描述 Resonance 中 Task 服务的职责、边界和处理语义。阅读完本文后，应该能回答三个问题：Task 为什么必须独立承担异步链路；为什么系统坚持“先写 Inbox，后推送”；以及 Task 当前已经把统一事件模型接到了什么程度。

---

## 1. Task 的定位

Task 是 Resonance 的事件消费与后置执行层。它不负责判断一条业务动作是否合法，也不负责决定数据库中的主事实应该怎样变化；这些事情在 Logic 中已经完成。Task 接手的是另一类问题：当系统已经确认一件事情成立之后，怎样把这个结果可靠地扩散给所有相关用户，怎样兼顾离线一致性与在线实时性，以及当某些推送路径失败时，怎样让系统仍然保持最终一致。

从整个系统来看，Task 的存在不是为了把“剩下的逻辑都放进异步服务”，而是为了把扩散、推送和补偿这类天然异步的问题，从 Logic 的事务边界中剥离出来。这样 Logic 可以专注于业务成立，Task 则专注于结果送达与最终一致。

---

## 2. 设计目标

Task 的设计主要服务于三件事。第一件事是消费由 Logic 产生的统一事件，并把它们变成面向接收者的可恢复事实。第二件事是完成写扩散，让同一个会话事件能够正确进入多个用户各自的 Inbox 视图。第三件事是尽可能把已成立事件实时送达在线用户，同时在送达失败时不破坏系统整体一致性。

这三个目标共同决定了 Task 的边界：它不是业务裁决层，而是异步执行层；它关心的是“结果如何扩散”，而不是“业务是否成立”。

---

## 3. 运行时位置

Task 位于 Logic 和 Gateway 之间的异步链路上。Logic 把已成立的业务结果通过 MQ 交给 Task，Task 在这里完成写扩散和在线推送，然后再通过 Gateway 把事件落到具体连接上。

### 3.1 架构图

```text
Logic ── MQ(NATS) ──▶ Task ── gRPC Push ──▶ Gateway ── WebSocket ──▶ Web
          │             │
          │             └── PostgreSQL / Redis（Inbox、在线路由等）
          │
          └── 已成立的统一事件
```

### 3.2 Task 在主链路中的作用

- 消费 Logic 发布的 `MQEvent`
- 根据 `ChatEvent.payload` 分派处理
- 先写接收者 Inbox
- 再查询在线路由并发起推送
- 在失败场景下维持最终一致而不是污染主链路

从这个位置可以看出，Task 的核心价值不在于“做很多业务判断”，而在于把一条已经成立的事件稳定地扩散出去。

---

## 4. 职责边界

### 4.1 负责什么

| 职责 | 说明 |
| ---- | ---- |
| MQ 消费 | 订阅并消费 Logic 发布的 `MQEvent` |
| 事件分发 | 按 `ChatEvent.payload` 选择对应 handler |
| 写扩散 | 把事件写入目标用户的 Inbox |
| 在线推送 | 查询在线路由并把事件推给对应 Gateway |
| 失败补偿语义 | 存储失败可重试，推送失败不污染主链路 |
| 派生状态处理 | 在必要时更新与送达相关的派生状态 |

### 4.2 不负责什么

| 不负责的事情 | 原因 |
| ------------ | ---- |
| 业务规则判断 | 这是 Logic 的职责 |
| 权限校验 | 这是 Logic 的职责 |
| 主事实写入 | 这是 Logic 的事务边界 |
| 协议适配与连接管理 | 这是 Gateway 的职责 |

Task 最需要克制的，就是不要越层去改写主事实。一旦异步层也开始直接更新消息主表、撤回状态或编辑内容，系统很快就会在重复消费、顺序抖动和补偿重试中失去业务一致性。

---

## 5. 核心处理语义

当前 Task 中最重要的处理约束，写在 `task/dispatcher/dispatcher.go` 里：先存储，后推送。这不是一个普通实现细节，而是整个系统可靠性设计的核心规则。

### 5.1 处理流程图

```text
MQEvent 到达 Task
  ├── 解析 ChatEvent
  ├── 按 payload 分派 handler
  ├── 先写 Inbox / 派生状态
  ├── 成功后查询在线路由
  ├── 按 Gateway 分组推送
  └── 完成消费
```

### 5.2 为什么必须先存储后推送

如果系统先推送，再写 Inbox，那么在线用户可能会先看到一条事件，但一旦断线重连，Inbox 中却找不到对应记录，最终状态就会不一致。反过来，如果系统先把事件写进 Inbox，再尝试推送，即使推送失败，用户后续仍然可以通过增量同步恢复同样的事件。也就是说，Push 只是在线优化，Inbox 才是最终一致的可靠兜底。

### 5.3 失败语义

| 失败点 | 处理方式 | 原因 |
| ------ | -------- | ---- |
| Inbox / 存储失败 | 返回错误，Consumer NAK 重试 | 因为事件尚未进入可恢复事实视图 |
| 在线推送失败 | 记录日志与指标，不 NAK | 因为 Inbox 已经承担一致性兜底 |
| 未知 payload | 直接跳过，避免无意义反复重试 | 防止异步链路被不支持类型卡死 |

Task 使用无缓冲 worker 交接，并把每个订阅实例的 JetStream pull 预取设为 1；它不会
把单实例 `worker_count` 写成共享 durable 的集群级 `MaxAckPending`。对于已从 broker
交付、正在等待 worker 或已经处理中的长任务，持久事件与 Agent stream 两个 Consumer
都通过 Genesis 的可选 `InProgress` 消息能力按 `progress_interval` 发送心跳，持续延长
JetStream Ack deadline。该间隔必须小于 broker 的 `ack_wait`；默认分别为 10 秒和
30 秒。这样重试预算和处理时延不会让同一条仍在执行的消息被提前重投。
这两项 JetStream 能力以 Genesis `v1.0.0-rc.2` 为运行时下限；发布前的
candidate-replace 门禁通过后，Resonance 仍需在 rc2 tag 可下载时更新 `go.mod`。

这套语义之所以成立，前提就是系统已经把“一致性”交给 Inbox，把“在线体验”交给 Push。只要这两个角色不混，Task 的行为就始终可解释。

## 6. 写扩散与在线推送

写扩散之所以属于 Task，而不属于 Logic，是因为二者关心的问题不同。Logic 关心的是“一条事件是否成立”，Task 关心的是“这条事件应该出现在谁的视图里”。一个会话中的消息、撤回、编辑、已读回执和会话更新，最终都需要以“对某个用户可见”的形式存在。把这一步放在 Task，可以让 Logic 只面对一次业务动作，而不用直接处理 N 个接收者视角的落地差异。

### 6.1 写扩散图

```text
ChatEvent + target_usernames
          │
          ▼
   构造多个 Inbox 记录
          │
          ▼
  批量写入接收者 Inbox
```

### 6.2 在线推送图

```text
已写入 Inbox 的事件
        │
        ▼
 查询目标用户在线路由
        │
        ▼
 按 Gateway 节点分组
        │
        ▼
 调用对应 Gateway Push 接口
        │
        ▼
 由 Gateway 落到本机在线连接
```

这种设计的价值在于，Task 既知道哪些用户需要看到事件，又不需要自己管理连接对象本身。连接层细节仍然被 Gateway 层吸收，Task 只负责事件分发与送达编排。

---

## 7. 统一事件模型在 Task 中的落地

Task 也是当前系统统一事件模型的一个重要验证点。当前 Dispatcher 已按 `message`、`recall`、`edit`、`read_receipt` 和 `session_update` 分支组织 handler 结构，而且其中 `message / recall / edit / read_receipt` 已经实际进入生产链路：Logic 产出统一事件，Task 负责把这些事件写入 Inbox 并推送给在线目标。

这说明 Task 并不是只拥有“看起来整齐的 handler 结构”，而是真正承担了统一事件分发层的角色。对于不同 payload，Task 的边界始终保持不变：主事实已经在 Logic 中成立，Task 只负责写扩散、在线推送和离线恢复兜底。

---

## 8. 当前实现结构

当前 Task 的主要实现落点包括：

- `task/task.go`：服务装配与生命周期管理
- `task/consumer/consumer.go`：MQ 消费与 ACK / NAK 语义
- `task/dispatcher/dispatcher.go`：统一处理入口
- `task/dispatcher/handler_*.go`：不同 payload 的分支处理
- `task/pusher/`：面向 Gateway 的推送客户端管理
- `task/README.md`：当前实现的职责说明

这些文件共同体现了一件事：Task 当前实现已经按“异步层”而不是“业务主层”组织起来了。

## 10. 小结

如果用一句话概括 Task，那么它是 Resonance 的异步扩散与送达层。它不决定业务是否成立，也不负责主事实写入；它负责的是把已经成立的事件稳定地扩散给正确的接收者，并在在线推送失败时仍然保持最终一致。只要“先写 Inbox，后推送”这条约束始终成立，Task 就会一直是系统里最清晰、也最可靠的异步执行层。
