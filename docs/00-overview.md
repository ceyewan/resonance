# 架构总览：从消息驱动到事件驱动

> 本文档是 Resonance 架构设计的总入口。阅读完本文后，应该能回答四个问题：系统为什么拆成现在这样；各个服务分别负责什么；一条消息是如何在系统中流转的；后续要看协议、数据库、服务设计、部署设计时分别应该去哪一篇文档继续读。

---

## 1. 系统目标与整体思路

Resonance 是一个专注于 IM 业务逻辑实现的系统。它的目标不是做成一个“什么都包”的平台，而是在即时通讯这个核心场景里，把消息发送、会话管理、在线状态、离线补偿和多端同步这些最关键的链路做扎实。围绕这个目标，系统逐步形成了现在的分层结构：Gateway 负责接入与连接，Logic 负责业务规则与主事实写入，Task 负责异步扩散与在线推送，Web 负责用户界面和本地交互，基础设施则由 PostgreSQL、Redis、NATS 和 Genesis 组件共同支撑。

这套架构的核心思路，是把“业务成立”和“结果送达”明确拆开。业务成立这件事，需要事务、一致性和权限校验，因此应该收敛在 Logic；结果送达到不同用户、不同终端，则天然是异步扩散问题，因此应该收敛在 Task。Gateway 既不负责主事实写入，也不负责异步扩散，它只负责把外部请求带进来、把内部事件送出去。只要这个边界保持清楚，系统后续继续增加撤回、编辑、已读、会话更新甚至 AI 会话能力时，就不需要每做一个功能都重写一套架构。

从当前演进方向看，Resonance 正在从“消息驱动”逐步过渡到“事件驱动”。过去一个 IM 系统如果只把消息本身当作唯一对象，那么一旦引入撤回、编辑、已读回执、多端同步等能力，协议、推送、存储和前端同步都会很快分裂成几套各自独立的逻辑。Resonance 选择用统一的 `ChatEvent` 作为会话域中的核心抽象，把消息、撤回、编辑、已读和会话更新都看作“会话中发生的用户可感知事件”，这样协议、异步链路和客户端处理模型都可以沿着同一套骨架演进。

## 2. 技术选型

系统当前的技术选型服务于两个目标：一是承载高并发连接与实时消息交互，二是保证业务主链路的一致性与可恢复性。后端使用 Go 构建三个核心服务与一个静态资源服务，前端使用 React 和 TypeScript 构建 Web IM 客户端，服务间同步调用使用 gRPC，异步事件链路使用 NATS JetStream，协议统一由 Protobuf 定义。

### 2.1 后端技术栈

| 类别 | 技术 | 作用 |
| ---- | ---- | ---- |
| 语言 | Go 1.26+ | 承载 Gateway、Logic、Task、WebServer |
| 组件库 | Genesis | 提供 connector、db、mq、auth、registry 等基础能力 |
| 服务间通信 | gRPC | Gateway → Logic、Task → Gateway 等内部调用 |
| 消息队列 | NATS JetStream | 承载 Logic → Task 的异步事件投递 |
| 协议 | Protobuf | 定义对外 API、内部服务和 MQ 事件结构 |

### 2.2 前端技术栈

| 类别 | 技术 | 作用 |
| ---- | ---- | ---- |
| 框架 | React 18 | 承载 Web IM 客户端 |
| 语言 | TypeScript | 约束前端协议与状态类型 |
| 构建工具 | Vite | 本地开发与生产构建 |
| 状态管理 | Zustand | 管理会话、消息和 UI 状态 |
| 通信 | ConnectRPC + WebSocket | 请求响应与实时事件接收 |
| 本地存储 | Dexie | 承接本地缓存与离线能力 |

### 2.3 基础设施选型

| 组件 | 技术 | 作用 |
| ---- | ---- | ---- |
| 主存储 | PostgreSQL 17 | 保存消息主事实、会话关系、Outbox、Inbox 等数据 |
| 路由与缓存 | Redis | 保存在线路由、序列号辅助状态与缓存 |
| 异步链路 | NATS | 承载事件投递与消费 |
| 服务发现 | etcd / registry | 承载服务注册与实例寻址 |

这套选型本身并不复杂，重点在于每种技术只解决它最擅长的问题。PostgreSQL 负责权威事实，Redis 负责快速状态，NATS 负责异步传播，gRPC 负责服务边界调用，WebSocket 负责与在线客户端保持实时连接。系统并不追求技术种类越多越好，而是希望每一层都尽量简单、直接、可验证。

## 3. 运行时架构

当前系统通过 `main.go` 使用 `-module` 参数启动不同角色，支持 `init`、`gateway`、`logic`、`task` 和 `web`。其中 `init` 是一次性数据库初始化入口，`web` 是静态资源托管服务，真正构成 IM 业务主链路的是 `gateway`、`logic` 和 `task`。这种统一入口、按模块启动的方式，使得开发、测试和部署都能围绕同一份构建产物展开，同时又能保持每个服务在运行时职责单一。

### 3.1 系统架构图

```text
Web ──HTTP/ConnectRPC──▶ Gateway ──gRPC──▶ Logic ──MQ(NATS)──▶ Task
 ▲         WebSocket        │                │                    │
 │                          │                └── PostgreSQL/Redis │
 └────────── WS ◀──── gRPC Push ◀────────────────────────────────┘
```

这张图里最关键的不是画出了几个框，而是明确了三条不同性质的链路。第一条是 Web 到 Gateway 的接入链路，它解决协议与连接问题；第二条是 Gateway 到 Logic 的业务链路，它解决权限、事务和主事实写入问题；第三条是 Logic 到 Task 的异步链路，它解决事件扩散、推送和补偿问题。反过来说，只要一个能力既想处理连接、又想直接改数据库、还想顺手把消息广播出去，那它大概率就是越过了这张图划定的边界。

### 3.2 服务职责

| 服务 | 一句话职责 | 不负责 |
| ---- | ---------- | ------ |
| **Gateway** | 协议转换、连接管理、鉴权中间件 | 业务规则、持久化 |
| **Logic** | 业务规则、主事实写入、Outbox 一致性 | 在线推送、写扩散 |
| **Task** | MQ 消费、写扩散、在线推送、补偿 | 业务裁决、主事实变更 |
| **Web** | 页面交互、状态管理、实时渲染 | 后端业务逻辑 |
| **Init** | 建表、迁移、种子数据初始化 | 常驻服务逻辑 |

### 3.3 服务通信方式

- **Web → Gateway**：ConnectRPC（HTTP）、WebSocket
- **Gateway → Logic**：gRPC
- **Logic → NATS → Task**：异步 MQ 事件
- **Task → Gateway → Web**：内部 Push gRPC + WebSocket 下发

这些通信方式背后有一个简单但非常重要的判断：同步调用只用来确认业务是否成立，异步链路才负责把结果扩散出去。这样发送方拿到 Ack 时，语义是“系统已经接受并持久化了这次业务动作”，而不是“所有接收者都已经在线收到了通知”。

## 4. 核心抽象：ChatEvent

在当前设计里，`ChatEvent` 是整个系统最重要的统一抽象。它定义在 `api/proto/common/v1/event.proto` 中，用来表示“会话里发生的一次用户可感知变化”。这种变化可以是发出一条消息，也可以是撤回一条消息、编辑一条消息、推进已读位点，或者修改会话元数据。系统不再把“消息”当成唯一对象，而是把这些变化统一表达为事件。

### 4.1 ChatEvent 结构

```text
ChatEvent
├── event_id
├── seq_id
├── session_id
├── from_username
├── timestamp_ms
└── oneof payload
    ├── message
    ├── recall
    ├── edit
    ├── read_receipt
    └── session_update
```

### 4.2 为什么要统一为事件

统一采用 `ChatEvent` 之后，系统的多个关键环节可以共享同一套数据骨架。Logic 生成的是 `ChatEvent`，MQ 里流转的是 `ChatEvent`，Task 写入 Inbox 的仍然是 `ChatEvent`，Gateway 推送给客户端的最终也应该是 `ChatEvent`。这样一来，后续新增能力时，主要变化只落在 payload 新增分支和对应处理逻辑上，而不会反复长出新的推送协议、新的离线同步结构和新的客户端事件通道。

### 4.3 当前实现状态

这里必须把“协议设计”和“业务落地”区分开。当前协议层已经为 `message`、`recall`、`edit`、`read_receipt` 和 `session_update` 预留了分支，但在真实业务实现中，`logic/service/chat.go` 当前完整打通的主要还是 `message`。这意味着系统已经有了统一事件模型的骨架，也已经有了消息主链路这个最关键的闭环，但其他事件类型仍处在逐步接入的阶段。理解这一点很重要，因为后续文档会在这个基础上继续展开：哪些是已经稳定的现状，哪些是已经确定方向但尚未完全落地的能力。

## 5. 核心消息链路

如果要快速理解系统当前是怎么工作的，最值得先看的是普通消息的主链路。因为这条链路最完整，也最能体现 Gateway、Logic、Task 三层各自解决的问题。它既解释了为什么要有同步调用和异步调用并存，也解释了为什么系统坚持用 Inbox 做兜底，而不是把在线推送当成唯一成功标准。

### 5.1 消息链路图

```text
Web                 Gateway              Logic                 NATS            Task              Gateway
 │                    │                    │                    │              │                    │
 │ 1. 发送消息         │                    │                    │              │                    │
 │───────────────────▶│                    │                    │              │                    │
 │                    │ 2. 鉴权并转 gRPC    │                    │              │                    │
 │                    │───────────────────▶│                    │              │                    │
 │                    │                    │ 3. 校验成员资格     │              │                    │
 │                    │                    │ 4. 生成 event/seq   │              │                    │
 │                    │                    │ 5. 事务写主表+Outbox│              │                    │
 │                    │                    │ 6. 返回 Ack         │              │                    │
 │                    │◀───────────────────│                    │              │                    │
 │ 7. 收到 Ack         │                    │                    │              │                    │
 │◀───────────────────│                    │                    │              │                    │
 │                    │                    │ 8. 异步投递 MQ      │              │                    │
 │                    │                    │───────────────────▶│              │                    │
 │                    │                    │                    │ 9. 投递事件   │                    │
 │                    │                    │                    │─────────────▶│                    │
 │                    │                    │                    │              │ 10. 先写 Inbox     │
 │                    │                    │                    │              │ 11. 再查在线路由   │
 │                    │                    │                    │              │ 12. 推给对应网关   │
 │                    │                    │                    │              │───────────────────▶│
 │                    │                    │                    │              │                    │ 13. 下发 WS 事件
 │                    │                    │                    │              │                    │───────────────▶ Web
```

### 5.2 这条链路说明了什么

这条链路首先说明，发送方收到 Ack 的时机早于接收方收到推送的时机。Ack 的含义是主事实已经在 Logic 里被接受并持久化，而不是异步扩散已经全部完成。这样做的目的，是把同步调用的职责限定在“确认业务成立”上，而不是让发送方等待整个异步扩散链路结束。

这条链路也说明，Task 的首要任务不是推送，而是写扩散。事件一旦从 MQ 到达 Task，Task 必须先把它写入接收者的 Inbox，然后才去尝试做在线推送。这样即使推送失败，接收方之后仍然可以通过增量同步恢复一致。当前 `task/dispatcher/dispatcher.go` 里明确采用了“先存储，后推送”的处理语义，这不是一个实现细节，而是整个系统可靠性设计的核心约束。

### 5.3 Push 与 Inbox 的关系

Resonance 把在线推送看作“在线优化路径”，把 Inbox 看作“最终一致兜底路径”。只要 Inbox 已经正确写入，即便推送失败，系统依然是正确的；因为用户稍后重新连上来，仍然可以通过拉取 Inbox 增量拿回同样的事件。反过来，如果推送先成功、Inbox 却没写进去，那么用户在线时可能看到一切正常，但一旦断线重连，历史状态就会不一致。这也是为什么系统必须坚持“先写 Inbox，后推送”的顺序。

## 6. 身份传递与边界约束

在身份传递上，系统采用一个很明确的约束：业务 body 不携带身份字段。Web 到 Gateway 使用 `Authorization: Bearer <token>` 完成认证，Gateway 在接入层完成 token 校验后，不再把原始 token 继续向下游转发，而是把已确认的用户名通过 gRPC metadata `x-username` 传给 Logic。Logic 的拦截器负责从 metadata 中恢复身份并写入上下文，后续业务代码统一从 context 中读取当前用户。

这条约束的意义在于，它把鉴权层和业务层干净地分开了。Gateway 关注的是“这个调用是否来自一个合法用户”，Logic 关注的是“这个已认证用户是否有权限做当前业务动作”。如果身份同时出现在 Header、metadata 和 body 里，就会很快出现多份来源不一致的问题，也会让协议变得越来越混乱。

在错误处理上，系统同样坚持边界清晰。业务失败通过 gRPC status 进行表达，而不是在响应结构里再塞一个自由文本 `error` 字段。这样 Gateway 和客户端可以用标准的错误处理方式理解失败原因，协议本身也不会被额外的非结构化字段污染。

## 7. 当前架构阶段

Resonance 当前不是一个所有设计都已全部完成的终态系统，而是一个主骨架已经清楚、消息主链路已经打通、其余能力正在沿着同一条架构路径补齐的系统。理解这一点很重要，因为这决定了我们在写文档时既不能只写理想态，也不能只写眼前的一小段实现细节。

### 7.1 已经稳定的部分

- Gateway、Logic、Task 的职责分层已经明确。
- `main.go` 的模块化启动方式已经稳定。
- `ChatEvent` 作为统一事件抽象已经建立。
- 普通消息主链路已经通过 Outbox、MQ、Inbox 和 Push 完整打通。
- Task 的“先写 Inbox，后推送”语义已经清楚。

### 7.2 正在继续完善的部分

- `recall`、`edit`、`read_receipt`、`session_update` 等 payload 的业务闭环。
- 更细粒度的离线补偿和多端同步设计。
- 围绕统一事件模型的前端本地状态同步与缓存策略。
- AI 会话与流式事件的接入方式。

这意味着后续文档的任务，不是重新定义另一套系统，而是在当前已经明确的骨架上，把协议、数据库、服务边界、关键流程和部署设计逐步讲清楚。

## 9. 小结

如果用一句话概括当前架构，那么 Resonance 是一个以 IM 业务为中心、以 `ChatEvent` 为统一抽象、由 Logic 保证主事实一致性、由 Task 完成写扩散与在线送达的分层微服务系统。它真正重要的地方不在于服务拆得有多细，而在于每一层都只处理自己该处理的问题。只要这个边界持续成立，后续新增能力时，增加的主要就是新的事件类型和新的处理逻辑，而不是重新生长出一套新的系统。
