# Gateway 设计

> 本文档描述 Resonance 中 Gateway 的职责、边界和运行方式。阅读完本文后，应该能回答三个问题：Gateway 为什么必须独立存在；它在系统里到底负责什么、不负责什么；以及客户端请求和内部推送是如何经过 Gateway 进入或离开系统的。

---

## 1. Gateway 的定位

Gateway 是 Resonance 的接入层。它离客户端最近，但并不拥有业务真相；它处理所有进入系统的协议，却不负责决定业务是否成立。对外，Gateway 面向 Web 客户端，承接 HTTP/ConnectRPC 请求和 WebSocket 长连接；对内，Gateway 面向 Logic 和 Task，既把客户端请求转成内部 gRPC 调用，也把 Task 发来的事件落到在线连接上。

从架构上看，Gateway 的存在不是为了多拆一个服务，而是为了把“协议与连接问题”从业务与一致性问题中隔离出来。浏览器更适合说 HTTP 和 WebSocket，Logic 更适合暴露稳定的内部 gRPC 服务，Task 则更适合通过内部 Push 接口把事件交给在线用户所在节点。Gateway 的职责，就是把这三种边界翻译清楚，而不是自己变成业务中心。

---

## 2. 设计目标

Gateway 的设计主要服务于三件事。第一件事是协议适配，让客户端使用浏览器友好的请求和连接方式，而不用直接面对内部服务协议。第二件事是连接管理，让系统可以追踪用户在线状态、维护长连接生命周期、把内部事件准确投递给当前在线终端。第三件事是身份收敛，把鉴权放在接入层完成，再向下游传播已认证身份，而不是让每个业务服务都自己反复解析 token。

这三件事共同决定了 Gateway 应该是一个“轻而稳定”的层。它可以非常忙，因为所有请求和所有在线连接都会经过它；但它不应该很重，因为只要它开始承担业务规则、主事实写入或异步扩散，整个系统的边界就会迅速变得混乱。

---

## 3. 运行时位置

Gateway 在当前系统中的位置如下图所示。它一端连着 Web，一端连着 Logic，另一端又要接收来自 Task 的内部推送，因此它同时是系统的北向入口和南向出口。

### 3.1 架构图

```text
Web ──HTTP/ConnectRPC──▶ Gateway ──gRPC──▶ Logic
 ▲         WebSocket        │
 │                          │
 └────────── WS ◀──── gRPC Push ◀──── Task
```

### 3.2 Gateway 在主链路中的作用

- 对 Web：承接请求、完成鉴权、管理连接、下发事件
- 对 Logic：作为唯一的外部请求转发入口
- 对 Task：作为在线推送的最终落点

从这个位置可以看出，Gateway 最重要的价值不是“做判断”，而是“做转换”和“做连接落地”。

---

## 4. 职责边界

### 4.1 负责什么

| 职责 | 说明 |
| ---- | ---- |
| 协议适配 | 把 HTTP/ConnectRPC、WebSocket、内部 Push 转成合适的内部调用或客户端下行包 |
| 鉴权 | 校验 token，识别当前用户身份 |
| 身份传递 | 把已认证用户名通过 `x-username` metadata 传给 Logic |
| 连接管理 | 维护 WebSocket 连接、心跳、读写循环和本地在线连接索引 |
| 请求转发 | 把客户端的业务请求转成对 Logic 的 gRPC 调用 |
| 推送落地 | 接收 Task 的 Push 调用，把事件投递给本机在线连接 |
| 在线状态上报 | 把连接变化同步给 Logic / Presence 服务 |

### 4.2 不负责什么

| 不负责的事情 | 原因 |
| ------------ | ---- |
| 业务规则判断 | 这是 Logic 的职责 |
| 主事实写入 | 这是 Logic 的事务边界 |
| 写扩散 | 这是 Task 的异步职责 |
| Outbox / MQ 可靠投递 | 这是 Logic 和 Task 的链路问题 |

这张表最重要的不是列出“不会做什么”，而是明确 Gateway 的边界。只要 Gateway 开始直接写数据库、开始自己判断会话权限、或者开始在本地做消息扩散，系统就会很快出现多个业务真相来源。

---

## 5. 核心入口

当前实现里，Gateway 同时承担三类入口。它们虽然都属于 Gateway，但语义完全不同，因此文档必须分开描述。

### 5.1 HTTP / ConnectRPC 入口

这类入口主要面向同步请求，例如登录、注册、会话列表、联系人、历史消息等。请求先经过 HTTP server 和中间件，再由具体 handler 调用 `logicclient` 转发给 Logic。这里的重点不在于 Gateway 自己处理了多少业务，而在于它为客户端提供了一个稳定、统一、浏览器友好的访问边界。

### 5.2 WebSocket 入口

WebSocket 入口主要面向实时交互。客户端建立长连接后，Gateway 负责管理连接生命周期、处理握手与读写循环，并把上行消息请求转成内部业务调用。对于下行方向，Gateway 则负责把内部统一事件编码为客户端可消费的包格式并发送到连接。WebSocket 在这里不是业务层，而是连接层和实时传输层。

### 5.3 内部 Push gRPC 入口

Task 在完成写扩散之后，会根据在线路由把目标用户分组到对应网关节点，再调用对应 Gateway 的 Push 接口。Gateway 收到内部 Push 请求后，根据用户名查找本地在线连接，找到则下发事件，找不到则视作当前节点上没有在线连接。这说明 Gateway 的内部 Push 接口本质上不是“业务接口”，而是“把系统内部事件落到具体连接上”的执行入口。

---

## 6. 身份与连接管理

Gateway 在系统里最重要的一项基础职责，是把鉴权和连接管理放在同一层解决。当前实现中，认证中间件会优先从 `Authorization` 头读取 Bearer token，也兼容查询参数中的 token。Gateway 自己不持有最终鉴权真相，而是通过内部逻辑客户端调用 Logic 的鉴权服务确认 token 是否有效，并拿到对应用户名。认证成功后，Gateway 把用户名放进请求上下文，后续 handler 和 WebSocket 分发逻辑都只使用这个已认证身份。

### 6.1 身份传递链路

```text
Web ── token ──▶ Gateway ── x-username metadata ──▶ Logic
```

### 6.2 为什么身份要在 Gateway 收敛

这样设计的好处，是让业务层不用面对“Header、body、query 里到底哪个身份才可信”这种问题。Gateway 解决“你是谁”，Logic 解决“你是否有权限做这件事”，边界因此非常清楚。同时，连接管理与身份管理天然耦合：Gateway 必须知道某条连接属于哪个用户，Task 才能根据在线路由把事件发到正确节点。

---

## 7. 在线推送路径

Gateway 是系统中在线事件离开后端、进入用户终端的最后一跳。Task 在异步层完成写扩散以后，只会把事件交给 Gateway，而不会直接接触 WebSocket 连接本身。这样做的好处，是让 Task 不需要知道连接层细节，Gateway 也不需要知道异步链路如何消费和补偿。

### 7.1 推送链路图

```text
Task ── 按在线路由分组 ──▶ Gateway PushService ──▶ 本地连接管理器 ──▶ WebSocket 下发
```

### 7.2 推送失败的语义

如果 Gateway 当前没有找到某个用户的本地连接，或者连接已经失效，这不应该被解释成业务失败。因为系统真正的一致性已经由 Inbox 保证，在线推送只是加速路径。Gateway 的职责是尽可能把在线事件送出去，而不是在推送失败时反过来决定业务是否成立。

---

## 8. 当前实现结构

当前 Gateway 的主要实现落点包括：

- `gateway/gateway.go`：服务装配与生命周期管理
- `gateway/middleware/auth.go`：认证中间件
- `gateway/transport/httpapi/`：HTTP / ConnectRPC 入口
- `gateway/transport/ws/`：WebSocket 握手、连接、分发与管理
- `gateway/logicclient/`：Gateway 到 Logic 的内部调用封装
- `gateway/pushserver/service.go`：Task 到 Gateway 的内部 Push 落点

这些目录本身不是文档的重点，但它们很好地说明了 Gateway 当前实现确实已经按“接入层”而不是“业务层”组织起来了。

## 10. 小结

如果用一句话概括 Gateway，那么它是 Resonance 的协议与连接层：负责把外部请求带进系统，把内部事件送到终端，但不拥有业务真相。它真正重要的地方，不是做了多少业务，而是始终没有越过自己的边界。只要这条边界保持清楚，Gateway 就会一直保持轻、薄、稳定。
